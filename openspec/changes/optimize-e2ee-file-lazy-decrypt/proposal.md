## 背景

当前 E2EE 媒体恢复逻辑会在收到实时消息或拉取历史消息时执行 `restoreContent`。图片、GIF 等有缩略图的内容只会先解密缩略图；普通文件没有缩略图时会退回到解密 `original`，导致大文件即使用户不点击下载，也会被下载、校验、解密并生成本地 Blob。

这会在大群、历史消息较多、文件较大的场景下放大带宽、CPU 和内存消耗，也会让进入会话或刷新页面变慢。

## 目标

- E2EE 普通文件在收到消息和拉取历史消息时只恢复文件元数据，不下载、不校验、不解密原文件。
- E2EE 普通文件在用户主动点击下载时，才下载密文原文件、校验哈希、解密并生成本地 Blob URL。
- 图片、GIF、私有上传表情等有缩略图的媒体保持现有体验：先解密缩略图展示，点击查看原图或播放原始资源时再加载原文。
- 解密后的普通文件 Blob 只做内存级缓存，不写入 IndexedDB、SQLite、localStorage 等持久化存储。
- 失败时保持安全关闭，不回退明文，也不暴露密钥、nonce 或明文字节。

## 非目标

- 不新增普通文件的发送入口和大小限制。
- 不改变服务端存储模型，服务端仍只保存密文文件和 E2EE 消息体。
- 不批量迁移历史明文文件。
- 不把解密后的文件持久化到本地数据库。

## 方案

`E2EEMediaCrypto.restoreContent` 根据 `originalContentType` 和是否存在 `thumb` 区分处理：

- 有 `thumb` 的图片/GIF/表情：继续解密 `thumb` 作为展示资源。
- 普通文件且没有 `thumb`：构造原始 `FileContent`，保留文件名、大小、类型，并挂载 `e2eeMedia` 元数据；`url` 保持为空，避免 UI 把密文 URL 当成可下载明文。
- `loadOriginal` 继续作为唯一的原文下载解密入口，并缓存 `originalBlobUrl`。

## 风险与处理

- 用户点击下载前文件 URL 为空：Web 需要识别 `content.e2eeMedia` 并主动调用 `loadMediaOriginal`。
- 下载失败或哈希校验失败：SDK 抛错，Web 展示失败提示，消息仍保留可重试状态。
- 同一页面重复点击下载：`loadOriginal` 复用 `originalBlobUrl`，避免重复下载解密。
