# 优化加密群成员设备目录缓存与预热

## 背景

Web 端切换到加密群会话时，SDK 会预热群成员 E2EE 设备目录，用于后续 sender-key envelope 分发。当前设备目录缓存时间较短，用户长时间不进入某个加密群后再次切换进去，容易重新请求 `/v1/channel/subscribers/e2e_devices`。在 300-1200 人大群中，这会造成打开会话或首次发送消息明显变慢。

## 目标

- 群成员 E2EE 设备目录支持长期缓存，减少切换加密群时的重复请求。
- 群成员 E2EE 设备目录需要持久化到浏览器本地缓存，刷新页面后仍可复用。
- 有可用旧缓存时，SDK 应先返回旧缓存，不阻塞打开会话和发送准备流程；同时在后台刷新新数据。
- 群成员变动、设备信息异常、发送/解密发现设备目录失效时，必须能主动失效缓存并重新获取。
- 服务端需要提供群 E2EE 设备目录版本信息，作为客户端错过群成员变更事件时的兜底校验。
- 保持 E2EE fail-closed：不能因为缓存或刷新失败而降级明文发送。

## 非目标

- 不改变 sender-key 的安全模型。
- 不复用同一套密钥给多端。
- 不把群成员设备目录缓存当成永久可信数据；长期缓存必须有主动失效机制。
- 不改变 `/v1/channel/subscribers/e2e_devices` 的响应结构。

## 已确认策略

- 长期缓存需要持久化到浏览器本地缓存。
- 服务端需要提供 `member_version/devices_version` 或等价版本接口，用于判断本地长期缓存是否仍然有效。
- 群成员变动事件作为最快失效路径；如果客户端错过事件，则通过版本校验、后台刷新和发送失败强制刷新兜底。
