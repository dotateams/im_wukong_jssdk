# 设计：SDK 加密群设备目录长期缓存与后台刷新

## 当前问题

SDK 的 `DeviceDirectory.getChanelSubscribersDevices()` 会请求 `/channel/subscribers/e2e_devices` 获取群内成员的 E2EE 设备列表。当前缓存时间过短，长时间不进入会话后缓存过期，切回加密群时会重新拉取全群设备。大群下这个请求耗时会放大，并影响预热和首次发送体验。

## 方案

### 1. 长期缓存

SDK 应将 `channelDevicesCache` 从短 TTL 缓存改为长期缓存：

- cache key 使用 `channel_id + channel_type`。
- 缓存内容包含标准化后的 `{ uid, devices }` 列表。
- 默认不因为时间自然过期。
- 缓存需要同时保存在内存和浏览器本地持久化存储中。内存用于当前页面快速访问，持久化存储用于刷新页面、重新打开 Web 后复用。
- 持久化缓存按账号、设备、频道隔离，避免不同账号或不同设备串用。
- 持久化记录需要包含 `member_version/devices_version`、保存时间、成员设备列表和必要的兼容字段。
- `forceRefresh=true` 必须绕过缓存并刷新。

### 2. stale-while-revalidate

当缓存存在且调用方没有强制刷新时：

1. 立即返回缓存数据。
2. 如果当前没有同频道刷新任务，则后台启动一次刷新。
3. 后台刷新成功后替换缓存。
4. 后台刷新失败时保留旧缓存，并只输出 debug/warn 日志，不阻塞 UI。

这样用户切换群会话时可以直接进入，刷新动作不影响首屏。

### 3. 版本校验与错过事件兜底

长期缓存不能只依赖群成员变动事件。客户端可能在离线、浏览器休眠、断线重连、页面关闭期间错过事件。因此 SDK 应采用多层兜底：

1. **事件失效**：收到群成员加入、退出、踢出、设备状态变更等事件时，立即失效对应频道的内存和持久化缓存。
2. **版本校验**：切换到加密群或发送前，如果本地缓存存在，应先使用缓存，同时后台请求服务端版本接口。若服务端 `member_version/devices_version` 与本地不一致，则重新拉取完整设备目录并替换缓存。
3. **发送失败兜底**：如果 sender-key envelope 分发、设备 key bundle 构建、加密发送出现“设备缺失/身份不匹配/成员目录不完整”类错误，必须强制刷新设备目录后重试一次。
4. **登录/重连兜底**：登录成功、断线重连成功后，可以对当前打开的加密群做一次轻量版本校验，不直接全量拉取设备目录。

### 4. 主动失效

缓存必须在以下场景失效：

- Web/SDK 收到群成员变动并调用 `invalidateGroupMemberCache(channel)`。
- sender-key envelope 分发发现成员设备缺失或 key bundle 不完整。
- 服务端返回设备目录校验失败、权限变化或频道不再是 E2EE。
- 用户退出登录或切换账号时清理当前账号关联的内存缓存。

### 5. 并发控制

- 同一频道同时只能有一个设备目录刷新请求。
- 多个调用方同时请求同一频道时，应复用同一个 in-flight promise。
- 有缓存时不等待 in-flight promise；无缓存时等待 promise。

### 6. 兼容性

- 保持 `e2e_devices` 到 `devices` 的字段兼容转换。
- 不改变加密发送、解密、sender-key envelope 的消息格式。
- 刷新失败不得导致明文降级。

## 风险

- 长期缓存可能短时间使用旧设备目录。通过群成员变动主动失效、版本接口校验和发送失败后的强制刷新兜底。
- 版本校验请求仍会产生少量接口调用，但响应应足够轻量，避免每次切群都拉取完整设备目录。
- 后台刷新过于频繁仍会产生压力，需要对同频道刷新做 in-flight 去重。
