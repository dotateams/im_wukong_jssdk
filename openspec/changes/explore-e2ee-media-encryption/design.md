## 设计概览

加密频道内的媒体消息采用“文件本体对称加密 + 元数据走现有 E2EE 消息加密”的模式。

发送端先在本地生成随机媒体密钥，使用 WebCrypto `AES-GCM` 加密图片、GIF 或用户私有上传表情文件，上传密文文件到现有文件服务。图片和 GIF 还需要由客户端生成缩略图，并对缩略图单独加密上传。上传成功后，SDK 构造一个普通业务媒体消息的安全封装，包含密文文件 URL、缩略图密文 URL、原始内容类型、尺寸、文件名、MIME、大小、哈希、加密算法、nonce 和媒体密钥。该封装再通过现有单聊/群聊 E2EE 消息链路加密后发送。

接收端先按现有 E2EE 流程解出媒体元数据，再下载密文文件，用元数据里的密钥和 nonce 在本地解密，生成 Blob URL 交给 Web UI 展示。解密后的 Blob 不做持久化保存，只在当前页面生命周期或内存缓存中存在。服务端、WuKongIM、数据库和对象存储都只能看到密文文件与加密消息体。

## 媒体内容范围

首批必须支持：

- 图片消息，内容类型 `2`。
- GIF 动图，当前 Web 上传 GIF 时最终也按图片类媒体上传和展示。
- 自定义表情和 Lottie 表情，内容类型 `12`、`13`。

本次不支持：

- 普通文件，内容类型 `8`。
- 语音、短视频。

这些类型后续可复用同一套媒体加密结构，但不纳入本次开发和验收。

## 消息结构

建议新增 SDK 内部内容类型 `MessageEncryptedMedia`，最终仍作为现有 `signalMessage` 的明文载荷被 E2EE 封装。解密后 SDK 应恢复成原业务内容类型，避免 Web 大量改 UI 判断。

推荐明文载荷结构：

```json
{
  "type": "encrypted_media",
  "version": 1,
  "original_content_type": 2,
  "media_kind": "image",
  "remote_url": "file/preview/chat/...",
  "mime": "image/png",
  "name": "image.png",
  "size": 123456,
  "width": 800,
  "height": 600,
  "algorithm": "AES-GCM",
  "original": {
    "url": "file/preview/chat/...",
    "key": "base64url(original-media-key)",
    "nonce": "base64url(12-bytes)",
    "sha256": "base64url(ciphertext-sha256)",
    "width": 1600,
    "height": 1200,
    "mime": "image/jpeg",
    "size": 123456
  },
  "thumb": {
    "url": "file/preview/chat/...",
    "key": "base64url(thumb-media-key)",
    "nonce": "base64url(12-bytes)",
    "sha256": "base64url(thumb-ciphertext-sha256)",
    "width": 240,
    "height": 180,
    "mime": "image/jpeg",
    "size": 12345
  }
}
```

说明：

- `original.key`、`thumb.key`、`nonce` 只存在于 E2EE 加密后的消息体内，不能明文存入普通图片消息。
- `original.url` 指向原图/原 GIF 密文文件，`thumb.url` 指向缩略图密文文件。
- `sha256` 用于下载后校验密文完整性。
- `original_content_type` 用于恢复 `ImageContent`、`GifContent` 或 `LottieSticker`。
- 原文件和缩略图必须使用不同的随机 key/nonce。

## 发送流程

1. Web 仍调用现有 `conversationContext.sendMessage(content)`。
2. SDK 判断频道是否 `is_e2e=true`。
3. 普通频道走原媒体上传逻辑。
4. 加密频道且内容为目标媒体类型时：
   - 读取 `content.file` 或可下载的表情资源。
   - 生成缩略图。图片缩略图建议最长边 `240px` 或 `320px`；GIF 缩略图使用静态首帧。
   - 分别为原文件和缩略图生成随机 `mediaKey` 和 `nonce`。
   - 使用 `AES-GCM` 分别加密原文件字节和缩略图字节。
   - 先后或并发上传原文件密文 Blob/File 和缩略图密文 Blob/File。
   - 上传成功后生成 `EncryptedMediaPayload`。
   - 使用现有单聊多设备或群 sender-key 流程加密该 payload。
   - 发送 `signalMessage`。
5. 本机发送端只在内存中持有明文 Blob 或 Blob URL，保证发送后立即可预览。

## 接收和历史流程

1. WebSocket 收到消息或历史接口拉取消息后，SDK 先执行现有 E2EE 解密。
2. 如果解密后的内容是 `encrypted_media`：
   - 优先下载 `thumb.url` 对应的缩略图密文文件。
   - 校验 `sha256`。
   - 使用对应的 `key` 和 `nonce` 解密。
   - 生成当前页面可用的 Blob URL。
   - 恢复成原业务内容对象，并把展示 URL 指向本地 Blob URL。
   - 用户点击查看大图或 GIF 播放时，再下载并解密 `original.url` 对应的原文件密文。
3. UI 层应继续使用现有 ImageCell、GifCell、LottieStickerCell。
4. 解密失败时展示明确失败状态，允许重试下载/解密，不允许自动降级明文。

## 自定义表情和 GIF

GIF 上传类资源应按图片媒体方式加密文件本体，同时生成一张静态首帧缩略图并单独加密上传。列表中优先展示静态缩略图，点击或需要播放时再解密 GIF 原文件。

自定义表情分两类处理：

- 公共自定义表情：资源本体继续复用公共表情库，不做一次性密文附件。消息里的表情 ID、包 ID、版本、URL、名称、类型等元数据走 E2EE 加密。这样服务端和 WuKongIM 看不到这条消息具体发了哪个表情，但不会产生重复上传和存储成本。
- 用户私有上传表情：按加密媒体处理，文件本体和缩略图都本地加密后上传。

如果后续要进一步降低公共表情的访问侧信道，可在打开表情面板时批量预加载公共表情包资源，避免“收到某条消息后才请求某个具体表情 URL”的行为过于明显。第一版不强制实现该优化。

## 文件大小和压缩策略

本次不新增 E2EE 专属大小限制，沿用现有发送入口和服务端上传限制。

当前 Web 图片入口会对普通图片做最大 `1600x1600`、质量 `0.9` 的压缩，GIF 保持原文件。E2EE 媒体应复用同样的压缩结果，再对最终要上传的文件字节做加密。

## 缓存策略

- 不持久化保存解密后的媒体 Blob。
- 发送端和接收端可以在内存中短期持有 Blob URL，用于当前页面立即展示。
- 页面刷新或重新登录后，SDK 重新解密消息体，拿到媒体密钥和密文文件链接，再按需下载密文文件并解密展示。
- 浏览器 HTTP 缓存即使命中，也只能缓存密文文件，不应缓存明文媒体。
- 退出登录、切换账号、切换设备时必须释放内存 Blob URL，并清理任何 E2EE 媒体临时缓存。
- 媒体密钥不需要单独持久化存储；它属于 E2EE 消息体的一部分。

## 缩略图策略

缩略图是指聊天列表里先展示的一张小尺寸预览图，而不是原图本身。普通明文图片可以由服务端生成或直接预览，但 E2EE 图片服务端看不到明文，无法生成可信缩略图。

第一版必须做客户端加密缩略图：

- 图片：发送端基于最终待上传图片生成一张小图，建议最长边 `240px` 或 `320px`，再单独 AES-GCM 加密上传。
- GIF：发送端提取首帧生成静态缩略图，再单独 AES-GCM 加密上传。
- 缩略图和原文件使用不同 key/nonce。
- 消息列表优先解密缩略图；用户点开预览时再解密原文件。
- 服务端只保存缩略图密文和原文件密文，不能生成、读取或转换缩略图。

## 安全要求

- 加密算法使用 WebCrypto `AES-GCM`，nonce 长度 12 字节，密钥 256 bit。
- 每个媒体文件必须使用独立随机密钥，不复用文本 Signal session key 直接加密大文件。
- 媒体密钥只通过现有 E2EE 消息体分发。
- 加密频道内媒体发送失败必须失败关闭，不允许静默回退明文。
- 日志不能打印媒体密钥、nonce、明文文件内容或 Blob URL 内部数据。调试日志只能打印类型、大小、是否密文、URL 是否为 Blob。

## 兼容规则

- 老的明文图片/GIF/表情历史继续按原消息类型展示。
- 新的 E2EE 媒体历史必须能从历史接口拉取后解密展示。
- 旧客户端不支持该能力时，在加密频道中无法查看新媒体消息，这是 E2EE 频道的预期兼容代价。
- 普通频道不改变任何媒体消息格式。

## 测试要求

- SDK 单元测试覆盖 AES-GCM 加解密、完整性校验失败、错误密钥失败、内存缓存命中。
- SDK 流程测试覆盖单聊、群聊、发送端本地预览、接收端实时消息、历史消息。
- Web 集成测试覆盖图片、GIF、自定义表情的发送、接收、刷新后历史展示。
- 回归测试覆盖普通频道媒体仍按明文旧逻辑发送。
- 需要 Chrome 实测两账号单聊、三账号群聊、刷新重登、历史拉取、旧明文历史兼容。

## 后续可扩展事项

- 是否在 Flutter 端实现同样的内存 Blob/临时文件缓存策略。
