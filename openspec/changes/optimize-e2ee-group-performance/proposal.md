# SDK 加密群历史与发送性能优化需求

## 背景

Web 加密群打开慢和首次发送慢，本质上有一部分来自 SDK E2EE 层：

- 历史消息解密需要 sender key、message key 和本地明文缓存协同。
- 首次发送群消息可能需要获取群成员设备、计算 memberHash、创建 sender key、为群内设备生成 envelopes 并上传。
- 大群中群成员设备数量多，任何逐用户、逐设备串行处理都会明显影响用户体验。

## 目标

- 提供更适合 Web 调用的加密群预热能力。
- 减少发送时重复获取群成员设备和重复计算 memberHash。
- 复用 sender-key 准备结果，降低首次发送延迟。
- 对群历史解密中的缺 key 恢复请求做并发去重和负缓存，避免进入群时大量 404 lookup。
- 为压测提供稳定的性能指标和测试入口。

## 非目标

- 不改变 Signal/sender key 的安全模型。
- 不把同一套密钥复用于多个设备。
- 不为了性能跳过 sender-key envelope 上传。
- 不让 E2EE 发送失败时退回明文。

## 待确认项

- sender-key envelope 上传必须在第一条群消息发送前完成，保证接收端及时解密；不得采用“先发消息、后台补 envelope”的模式。
- 群成员设备缓存不使用固定时间过期，默认长期缓存；缓存有效性由 `memberHash`、设备版本或群成员变动事件控制。只有拿不到可靠版本信息时，才允许使用短 TTL 兜底。
- 大群 sender-key envelope 构建并发必须可配置。Web 第一版建议传入 20；SDK 默认 10 作为兜底。压测脚本需要覆盖 5、10、20、30、50。
