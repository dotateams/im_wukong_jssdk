## 背景

当前 E2EE 文件上传已经可以把文件加密后上传，但加密格式仍是单个 AES-GCM 密文。发送大文件时，客户端需要把整文件读入内存加密；点击下载时，也需要把整份密文下载成 Blob，再整块解密成 Blob。这样在几十 MB 以上就容易造成页面长时间“解密中”、浏览器主线程卡顿、内存暴涨，无法满足生产环境 1GB 文件的使用目标。

同时，当前上传链路缺少断点续传能力：网络中断、刷新页面、浏览器崩溃后，只能重新加密并重新上传整个文件。大文件在弱网下体验不可接受，也会增加 MinIO、API 和客户端的重复流量。

## 目标

- E2EE 文件支持分片加密：每个分片独立加密、独立校验、独立上传。
- E2EE 文件支持断点续传：上传中断后可从已完成分片继续，不重新上传已成功分片。
- E2EE 文件支持分片下载和分片解密：点击下载时按分片拉取、校验、解密、写出，避免整文件进入浏览器内存。
- 继续保证端到端加密：服务端、MinIO、WuKongIM 只能看到密文分片和加密元数据，不能看到明文文件、明文分片密钥或主密钥。
- 保持普通频道、非 E2EE 文件和小文件现有行为兼容。
- 支持 1GB 文件作为第一阶段生产目标。
- 支持 Web 端优先落地，数据结构为后续 Flutter 端实现预留兼容。

## 非目标

- 不在第一版实现服务端明文查毒、在线预览、全文索引。
- 不要求旧客户端可以下载新分片 E2EE 文件；旧客户端应展示“请升级最新客户端”。
- 不修改 WuKongIM 底层消息投递协议，只在消息 payload 中携带新的 E2EE 文件清单元数据。
- 不在第一版做跨设备共享本地下载进度；断点续传以当前设备本地状态为准。
- 不在第一版做 P2P 分片传输，所有分片仍通过现有 API/MinIO 存储链路。

## 推荐方案

采用“客户端分片加密 + 服务端分片会话 + MinIO 分片对象 + 完成后 manifest 消息”的方案。

客户端选择文件后按固定大小切片。每个分片使用独立随机 nonce 和派生密钥加密，并生成密文 SHA-256。SDK 创建上传会话，查询服务端已有分片，跳过已上传分片；未上传分片逐个或小并发上传。所有分片上传成功后，客户端发送消息，消息中携带 `e2eeMedia.version = 2` 的 manifest，包括分片大小、总大小、文件名、MIME、每个分片密文路径、密文 hash、nonce、分片序号等必要信息。

下载时，SDK 读取 manifest，逐片下载、校验、解密，并写入本地文件。Web 优先使用 File System Access API 或 StreamSaver 类方案实现流式写出；不支持流式写文件的浏览器降级为小文件 Blob 下载，大文件提示使用桌面端或支持的浏览器。

## 备选方案

### 方案 A：继续单文件密文，仅增加 HTTP Range

优点是服务端改动小。缺点是 AES-GCM 单密文不能安全任意分段解密，仍需整块密文和整块明文进入内存，不能解决卡死问题。不推荐。

### 方案 B：使用 MinIO Multipart Upload 作为唯一分片层

优点是复用对象存储 multipart 能力。缺点是 E2EE 每片加密、断点状态、下载解密 manifest 仍然要由客户端和业务服务维护；直接依赖 MinIO multipart 状态会把业务兼容性绑死在对象存储实现上。不作为第一选择。

### 方案 C：业务分片对象 + 服务端会话记录

优点是实现清晰、可测试、可跨对象存储迁移，客户端能精确恢复进度，下载可按 manifest 逐片处理。缺点是服务端需要新增分片上传会话、分片状态查询、完成/取消接口和清理任务。推荐采用。

## 影响范围

- `im_wukong_jssdk`：新增 chunked media v2 加密、上传、恢复、下载、校验、进度回调、错误恢复。
- `TangSengDaoDaoWeb`：文件发送 UI、上传进度、暂停/重试/继续、下载进度、文件保存、错误提示。
- `TangSengDaoDaoServer`：新增 E2EE 文件分片上传会话 API、分片状态 API、完成 API、清理任务、大小限制和权限校验。
- `MinIO`：继续作为密文分片存储，不理解 E2EE 内容。
- `WuKongIM`：只投递 manifest 消息，不理解分片内容。

## 兼容策略

- 旧 `e2eeMedia.version` 为空或 `1` 的消息继续走现有单密文逻辑。
- 新分片文件使用 `e2eeMedia.version = 2`。
- 新客户端收到 version 2 文件时展示正常文件卡片并支持下载。
- 旧客户端收到 version 2 文件时无法解密，应显示升级提示，不应崩溃。
- 普通明文频道文件不受影响。

## 风险

- 分片数量过多会增加 API 调用次数，需要限制分片并发和分片大小。
- 浏览器流式写文件能力不一致，需要明确降级策略。
- 上传会话和未完成分片会产生垃圾对象，需要服务端 TTL 清理。
- 分片 manifest 过大可能增加消息 payload，需要控制分片大小，避免把几千个分片塞进消息。
- 客户端本地断点状态与服务端状态可能不一致，需要以服务端已完成分片为准重新校准。

## 待确认问题

1. 第一版分片大小建议为 `8MB` 还是 `16MB`？我建议 `8MB`，1GB 大约 128 片，manifest 可控，重传粒度也合理。
2. Web 是否必须支持所有浏览器大文件流式下载？如果必须，会需要引入 StreamSaver 或桌面端专用下载桥；如果接受降级，Chrome/Edge 优先用 File System Access API。
3. 上传是否需要“暂停/继续”按钮？还是第一版只做自动断点续传和失败重试？
4. 未完成上传会话保留多久？建议服务端保留 7 天，客户端本地状态也保留 7 天。
5. 分片上传并发建议默认 `3`，是否可以根据网络情况后续配置？
