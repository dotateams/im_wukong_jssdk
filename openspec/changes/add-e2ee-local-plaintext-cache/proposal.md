# E2EE 本地明文缓存与 sender key 长期持久化需求

## 背景

当前 E2EE 历史消息在刷新页面、重启浏览器或重新进入加密群时，仍需要从服务端密文消息恢复展示。文本消息只做有限时间的本地明文缓存，媒体缩略图依赖临时 `blob:` URL，sender key 也可能在重启或本地记录缺失后触发重新查找。

这会导致用户已经看过的加密历史消息，在再次打开时仍可能因为缺少 sender key、message key 或媒体缓存而变慢，甚至显示“无法解密”。

## 目标

- SDK 必须支持 E2EE 文本消息解密后的本地明文长期缓存，不设置过期时间。
- SDK 必须支持 sender key 长期本地持久化，默认不主动刷新或过期。
- 只有当本地 sender key 缺失、失效或无法解密当前消息时，才允许重新向服务端拉取可用 key envelope。
- 缓存必须按账号、设备、频道、消息维度隔离，避免不同账号、不同设备或不同频道之间串用明文和密钥。
- 图片、GIF、自定义表情等媒体消息必须支持缩略图解密结果缓存，刷新页面后优先复用本地缩略图缓存。
- 普通大文件仍然保持懒解密：只有用户点击下载时才下载密文、校验并解密原文件。
- 缓存未命中时，必须回退到密文消息重新解密。

## 非目标

- 不改变服务端“只保存密文消息和密钥信封”的模型。
- 不把大文件原文自动长期缓存到本地。
- 不把本地明文缓存同步到服务端或其他设备。
- 不保证新设备能解密加入设备之前没有 key 的历史消息。
- 不在本次需求中实现 Flutter 端代码，但后续 Flutter 端应遵循同一产品策略。

## 安全取舍

该需求明确选择“本机可用性优先”：解密后的文本明文和缩略图会长期保存在当前设备本地，退出登录前不自动过期。

风险是：如果用户设备、浏览器 Profile、SQLite/IndexedDB/OPFS/localStorage 数据被他人取得，对方可能直接读取已经缓存的明文历史消息或缩略图。该风险需要在 Web 端退出登录提示和技术文档中明确告知。

## 待确认项

- 退出登录清理范围默认理解为“当前浏览器当前账号当前设备”的 E2EE 本地缓存、sender key 和缩略图缓存，不影响同一账号在其他设备上的缓存。
- 文本明文缓存默认包含单聊和群聊的 E2EE 文本消息，以及可文本化展示的系统/业务消息；普通文件原文不纳入长期缓存。
